# 🛠️ DevOps Lab — Завдання

> **Made in Ukraine** 🇺🇦 | Авторка: [TEZv](https://github.com/TEZv)

Практичний набір DevOps-завдань, від початкового до просунутого рівня.
Кожне завдання самостійне і спирається на попередні.

> **Як користуватись**: Відкрийте цей репозиторій у [GitHub Codespace](https://github.com/codespaces) — усі інструменти (Docker, Terraform, Kubernetes, GitHub CLI) вже встановлені. Починайте з Рівня 1 і рухайтесь далі.

---

## 🟢 Рівень 1: Docker

### Завдання 1.1 — Збірка та запуск

**Мета**: Зрозуміти життєвий цикл Docker-образу.

У директорії `docker/` знаходиться простий `Dockerfile` та `index.html`.

1. Змініть `index.html` — додайте щось своє (особисте повідомлення, лічильник, що завгодно).
2. Зберіть Docker-образ.
3. Запустіть контейнер і перевірте, що сторінка віддається.

**Питання для роздумів**:
- Що робить кожен рядок у `Dockerfile`?
- Що станеться, якщо змінити HTML, але не перезібрати образ?

---

### Завдання 1.2 — Багатосервісний docker-compose

**Мета**: З'єднати кілька контейнерів між собою.

Зараз у `docker-compose.yml` лише один сервіс (`web`). Додайте другий:

1. Додайте сервіс `redis` до `docker-compose.yml`.
2. Налаштуйте залежність web від redis.
3. Перевірте, що обидва контейнери працюють і можуть спілкуватись.

**Питання для роздумів**:
- Як контейнери знаходять один одного у Docker Compose?
- Що станеться, якщо redis запуститься раніше, ніж web буде готовий?

---

### Завдання 1.3 — Багатоетапна збірка (Multi-Stage Build)

**Мета**: Оптимізувати Docker-образи для production.

Створіть багатоетапну збірку:

1. Етап 1: Використайте Node.js-образ для збірки статичного сайту (або будь-якого інструменту збірки).
2. Етап 2: Скопіюйте лише результат збірки у nginx-образ.
3. Фінальний образ має бути якомога меншим.

**Питання для роздумів**:
- Чому фінальний образ менший при багатоетапній збірці?
- Що залишається у build-етапі і не потрапляє у фінальний образ?

## 🟡 Рівень 2: Terraform

### Завдання 2.1 — Читання та план

**Мета**: Зрозуміти workflow «спочатку план, потім застосування».

У директорії `terraform/` є базова конфігурація, яка створює GitHub-репозиторій.

1. Виконайте `terraform init` у директорії `terraform/`.
2. Виконайте `terraform plan` і уважно прочитайте вивід.
3. Відповідь: які ресурси будуть створені? Які значення обчислюються?

**Питання для роздумів**:
- Що насправді робить `terraform plan`?
- Чому це безпечніше, ніж одразу `terraform apply`?

---

### Завдання 2.2 — Змінні та параметризація

**Мета**: Зробити Terraform-код придатним для повторного використання.

Зараз назва репозиторію захардкожена. Рефакторіть:

1. Створіть файл `variables.tf` зі змінною для назви репозиторію.
2. Замініть захардкожену назву у `main.tf` на посилання на змінну.
3. Створіть файл `terraform.tfvars` зі значенням за замовчуванням.
4. Виконайте `terraform plan` — результат має бути ідентичним.

**Питання для роздумів**:
- Яка різниця між значенням за замовчуванням у `variable` та у `terraform.tfvars`?
- Як перевизначити змінну без редагування файлів?

---

### Завдання 2.3 — Вивід (Outputs)

**Мета**: Відкрити корисну інформацію після створення інфраструктури.

1. Створіть файл `outputs.tf`.
2. Виведіть щонайменше: назву репозиторію, його URL та clone URL.
3. Виконайте `terraform plan` — зверніть увагу на секцію outputs внизу.

**Питання для роздумів**:
- Коли обчислюються значення outputs — при plan чи при apply?
- Як інший Terraform-модуль може використати ці outputs?

---

### Завдання 2.4 — Додаткові ресурси

**Мета**: Комбінувати кілька Terraform-ресурсів разом.

Додайте щонайменше один з наступних ресурсів до `main.tf`:

- `github_branch_protection` для гілки `main`.
- `github_team` і прив'яжіть його до репозиторію.
- `github_issue_label` з власними кольорами.

**Питання для роздумів**:
- Як працюють залежності між ресурсами у Terraform?
- Що станеться, якщо посилатись на атрибут ресурсу, який ще не створено?

## 🔴 Рівень 3: Kubernetes

### Завдання 3.1 — Перевірки здоров'я (Health Checks)

**Мета**: Дати Kubernetes знати про стан вашого додатку.

У `k8s/deployment.yml` — базовий Deployment без перевірок.

1. Додайте `livenessProbe` — як Kubernetes має перевіряти, чи nginx живий?
2. Додайте `readinessProbe` — коли Kubernetes має починати надсилати трафік на под?
3. Застосуйте маніфест і перевірте проби через `kubectl describe pod`.

**Питання для роздумів**:
- Яка різниця між liveness та readiness пробами?
- Що станеться, якщо liveness probe впаде? А readiness?

---

### Завдання 3.2 — Автомасштабування

**Мета**: Дозволити Kubernetes автоматично масштабувати додаток.

1. Створіть ресурс `HorizontalPodAutoscaler` (HPA).
2. Налаштуйте масштабування від 2 до 10 реплік за використання CPU.
3. Застосуйте та перевірте статус через `kubectl get hpa`.

**Питання для роздумів**:
- Які метрики, окрім CPU, може використовувати HPA?
- Чому HPA потребує встановлених resource requests на поді?

---

### Завдання 3.3 — ConfigMap як Volume

**Мета**: Відокремити конфігурацію від образів контейнерів.

Замість того, щоб «запікати» HTML у Docker-образ:

1. Створіть `ConfigMap` з HTML-контентом.
2. Змонтуйте ConfigMap як volume у Deployment.
3. Перевірте, що сторінка віддається з ConfigMap, а не з образу.

**Питання для роздумів**:
- Що станеться з запущеним подом, якщо оновити ConfigMap?
- Коли варто використовувати ConfigMap, а коли Secret?

## 💀 Рівень 4: CI/CD

### Завдання 4.1 — Розширення пайплайну

**Мета**: Побудувати повний CI/CD пайплайн.

У `ci-cd/pipeline.yml` є базові стадії build та terraform plan.

1. Додайте стадію `test`, яка виконується після `build`.
2. Додайте стадію `deploy`, яка застосовує Kubernetes-маніфести.
3. Зробіть так, щоб `deploy` запускався лише для гілки `main`.

**Питання для роздумів**:
- Яка різниця між `needs` та `runs-on` у GitHub Actions?
- Як передавати артефакти між джобами?

---

### Завдання 4.2 — Ручне підтвердження

**Мета**: Додати захисний шлюз перед production-деплоєм.

1. Додайте крок ручного підтвердження перед стадією `deploy`.
2. Використайте GitHub Environments з required reviewers.
3. Перевірте: пайплайн має призупинятись і чекати на підтвердження перед деплоєм.

**Питання для роздумів**:
- Які компроміси між ручними підтвердженнями та автоматичними деплоями?
- Як реалізувати «автоматичний відкат», якщо деплой зазнає невдачі?

## 🏆 Бонусні завдання

Ці завдання комбінують кілька інструментів і вимагають креативного мислення.

### Бонус 1 — Terraform + Docker Provider

Використайте [Terraform Docker provider](https://registry.terraform.io/providers/kreuzwerker/docker/latest), щоб збирати та запускати Docker-контейнери через Terraform замість Docker CLI. Порівняйте обидва підходи.

### Бонус 2 — GitOps з ArgoCD

Встановіть ArgoCD у ваш Minikube-кластер і налаштуйте його на синхронізацію Kubernetes-маніфестів з вашого GitHub-репозиторію. Тепер кожен `git push` тригерить деплой.

### Бонус 3 — Тести інфраструктури

Напишіть тестовий скрипт (bash або Python), який перевіряє інфраструктуру після `terraform apply`:
- Чи доступний GitHub-репозиторій?
- Чи встановлені правила захисту гілок?
- Чи створені мітки?
